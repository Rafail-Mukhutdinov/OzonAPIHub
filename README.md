## 🎯 О проекте

OzonAPIHub — это профессиональный инструмент для селлеров, позволяющий автоматизировать сбор данных, анализировать прибыльность и управлять расходами в режиме реального времени.

- 🐍 **Backend**: FastAPI, SQLAlchemy, PostgreSQL.
- 📱 **Frontend**: Flutter Web/Android/iOS с единой базой кода.

### Основные фичи
- **Multi-tenancy**: Полная изоляция данных пользователей на уровне БД.
- **Безопасность**: Шифрование API-ключей (Fernet) и JWT-авторизация.
- **Аналитика**: Детальные отчеты по FBO, статусам, SKU и прибыльности.
- **Синхронизация**: Автоматический сбор данных с Ozon API в фоновом режиме.
- **Логирование**: Раздельные логи для системы и каждого пользователя с ротацией файлов.

## ⚙️ Архитектура синхронизации (Engine)

Движок синхронизации построен на **ARQ + Redis** и обеспечивает надёжный сбор данных без потерь даже при перебоях API Ozon или простое сервера. Ниже — ключевые подсистемы и алгоритмы.

### 1. Adaptive Polling (Адаптивный планировщик)
Частота опроса Ozon рассчитывается индивидуально для каждого продавца на основе времени последней продажи (по МСК):
- **Турбо (1 мин)** — продажа менее часа назад.
- **Стандарт (5 мин)** — продажи были сегодня.
- **Эко (15 мин)** — активности давно нет.

Планировщик запускается каждую минуту, но решение о реальном запросе к API принимает внутри цикла — это снижает нагрузку на Ozon и экономит лимиты.

### 2. Smart Gap Filling (Интеллектуальный поиск «дыр»)
- **Для заказов** (`OrderPosting`) стартовая дата синхронизации вычисляется от `max(created_at)` минус 12 часов — это закрывает микро-пропуски из-за задержек API.
- **Для начислений** (`OzonAccrual`) реализован отдельный алгоритм **Hole Detection**.

### 3. Hole Detection (Поиск и заполнение пробелов в финансах)
Решает проблему «слепой зоны», когда в БД есть свежие данные, но внутри диапазона есть дыры (например, отсутствуют 7–12 июля при наличии 13–16 июля):
- `find_accrual_date_gaps()` сканирует последние 30 дней через `SELECT DISTINCT date` и находит отсутствующие даты.
- Дедупликация: даты, которые покроются стандартным окном, исключаются через `set`-comprehension (O(1)).
- Лимитирование: за один цикл закрывается не более `MAX_GAPS_PER_CYCLE = 10` дыр — защита от таймаутов адаптивного планировщика.
- Нормализация времени: `since` сбрасывается к началу дня (`replace(hour=0...)`) для корректного сравнения с `DateTime` колонкой.

### 4. Атомарные транзакции (ACID)
В `enrich_accruals_from_ozon` удаление старых записей и вставка новых выполняются **в рамках одной транзакции**:
- При ошибке/таймауте API `db.rollback()` отменяет и DELETE, и INSERT → старые данные сохраняются.
- При ложнопустом ответе API используется `rollback()` вместо `commit()` — данные не обнуляются.
- Постраничная пагинация корректно обрабатывает пустые страницы с `last_id`.

### 5. Система блокировок (Mutex / «эффект снежного кома»)
Предотвращает наложение циклов синхронизации друг на друга:
- Флаг `SyncStatus.is_syncing = True` устанавливается и **коммитится до** запуска тяжёлой функции.
- Снятие флага строго в блоке `finally` с предварительным `db.refresh(status)` — защита от `DetachedInstanceError`.
- Метрики времени (`sync_started_at`, `sync_completed_at`, `last_sync_attempt_at`) точно соответствуют модели `SyncStatus`.

### 6. Двойной источник финансовых данных
Для 100% покрытия расходов синхронизируются **оба** API Ozon:
- **`/v1/finance/accrual/by-day`** (`OzonAccrual`) — детальные начисления: выручка, комиссия, доставка, сервисы.
- **`/v3/finance/transaction/list`** (`Cost`) — общие транзакции: реклама, хранение и прочие услуги. Защита от дублей через теги `[ID:operation_id]` в `notes`.

### 7. Полный справочник услуг Ozon
В `routes/analytics.py` внедрён словарь `OZON_SERVICE_TYPES` из **119 типов операций** (ID 1–117, 120, 305, 1000) с человекочитаемыми названиями. Используется только для отображения в отчётах и выпадающих списках — **логика категоризации** (комиссия/логистика/реклама/хранение) оперирует числовыми ID и не зависит от названий.

## 🧪 Применённые технологии и паттерны

| Технология / Паттерн | Где применяется |
|---|---|
| **FastAPI + asyncio** | Асинхронные эндпоинты и неблокирующие запросы к Ozon API |
| **ARQ + Redis** | Фоновый воркер, очереди задач (Backfill, Range Sync), cron-расписание |
| **SQLAlchemy ORM** | Модели, агрегации (`func.max`, `func.sum`), `with_for_update()` (row-level lock) |
| **SAVEPOINT (`begin_nested`)** | Изоляция ошибок отдельных заказов внутри пакетной транзакции |
| **asyncio.Semaphore** | Ограничение конкуренции (`ENRICH_CONCURRENCY`) при массовом обогащении |
| **Fernet (симметричное шифрование)** | Шифрование API-ключей Ozon в БД (`utils/encryption.py`) |
| **JWT (JSON Web Tokens)** | Авторизация и мульти-тенантная изоляция данных |
| **Adaptive Polling** | Динамические интервалы 1/5/15 мин на основе активности продаж |
| **Smart Gap Filling / Hole Detection** | Автоматическое восстановление пропущенных данных |
| **Idempotent DELETE+INSERT** | Безопасная перезапись данных за день без дубликатов |
| **Batch N+1 optimization** | Предзагрузка статусов и ID всей пачкой через `IN (...)` |

## 🏗️ Структура проекта

- `/routes`: API эндпоинты (аналитика, заказы, расходы, аутентификация).
- `/services`: Бизнес-логика синхронизации и интеграции с Ozon.
- `/db`: Модели данных SQLAlchemy.
- `/utils`: Утилиты шифрования, авторизации, валидации и логирования.
- `/ozon_sales_dashboard`: Исходный код Flutter-приложения.
