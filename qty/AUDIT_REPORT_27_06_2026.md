## 🚨 КРАТКАЯ СУТЬ ПРОБЛЕМЫ

Код дашборда (`routes/analytics.py`) **не умеет отличать возвраты товаров от комиссий Ozon**. Из-за этого все комиссии, эквайринг и логистика ошибочно учитываются как "возврат товара". Это приводит к тому, что себестоимость уходит в глубокий минус (`-2918 ₽`), а формула прибыли искусственно завышается (`3029 ₽`).

## 🔥 КРИТИЧЕСКАЯ ОШИБКА #1: Комиссии ошибочно считаются возвратами

**Файл:** `routes/analytics.py`  
**Строки:** 310–332

Разработчик API попытался определить тип операции (продажа или возврат) только по знаку `amount` внутри категории `POSTING`.

```python
    for r_sku, r_cat, r_amt, r_qty in accrual_items_raw:
        val = float(r_amt or 0)
        qty = int(r_qty or 1)
        
        # Если это запись о товаре в POSTING
        if r_cat == 'POSTING' and r_sku:
            # Разделяем на выручку и возвраты
            if val > 0:
                total_sales_revenue += val
                # ...
                total_cost_price += (cp * qty)
            elif val < 0:  # <--- ФАТАЛЬНАЯ ОШИБКА ЗДЕСЬ
                total_returns_amount += abs(val)
                # Вычитаем себестоимость возврата
                cp = get_product_cost(db, current_user.id, int(r_sku), calculation_date)
                total_cost_price -= (cp * qty)
```

### Почему это ломает отчёт?

В сервисе `services/enrichment.py` (строки 311–351) данные сохраняются в БД (`OzonAccrual`) так:
1. Выручка: `operation_type='revenue'`, `amount=1000`, `sku=123`, `accrued_category='POSTING'`
2. Комиссия: `operation_type='expense'`, `amount=-200`, `sku=123`, `accrued_category='POSTING'`
3. Логистика: `operation_type='expense'`, `amount=-100`, `sku=123`, `accrued_category='POSTING'`

Когда `analytics.py` читает эти строки из БД:
- Для выручки (`val=1000`) он правильно добавляет себестоимость.
- Для **комиссии** (`val=-200`) он видит `< 0` и решает: *"Ага, это возврат товара!"*
  - Он добавляет `200` в `total_returns_amount`.
  - Он **вычитает** себестоимость товара из `total_cost_price`.

В результате, за каждый проданный товар себестоимость вычитается столько раз, сколько услуг (комиссия, эквайринг, доставка) к нему применено.

**Влияние на дашборд 27.06:** Себестоимость ушла в минус (`-2918 ₽`), потому что она вычиталась за каждую комиссию и логистику, хотя товара в наличии не стало.

### Почему скрипт считает верно?

В `test_accruals_by_day.py` (строки 169–218) логика построена принципиально иначе. Скрипт берет сырые данные и четко разделяет ключи:
```python
# 1. Выручка и Возвраты товаров
sale_amt = parse_amount(comm.get("sale_amount"))
if sale_amt > 0:
    # Считаем себестоимость при продаже
elif sale_amt < 0:
    # Вычитаем себестоимость при возврате

# 2. Комиссия (С учетом знака!)
comm_amt = parse_amount(comm.get("commission"))
# 3. Доставка и сервисы (С учетом знака!)
```
Скрипт никогда не путает комиссию с возвратом товара, потому что берет значения из разных блоков JSON (`sale_amount` vs `commission`).

## 🔥 КРИТИЧЕСКАЯ ОШИБКА #2: Двойной учёт расходов и развал формулы прибыли

**Файл:** `routes/analytics.py`  
**Строки:** 344–412

Из-за Ошибки #1 переменная `total_returns_amount` уже содержит в себе сумму всех комиссий и логистики за день.

Чуть ниже в коде (строки 344–364) дашборд делает **второй проход** по расходам и заново суммирует их:
```python
    for tid, amt_sum in accruals_summary:
        abs_expense = -float(amt_sum or 0)
        cat_name = get_expense_category(tid)
        
        if cat_name == "Комиссия Ozon": total_commission += abs_expense
        elif cat_name == "Эквайринг": total_acquiring += abs_expense
        elif cat_name == "Логистика (FBO/FBS)": total_logistics += abs_expense
```

В итоге формула прибыли (строка 412):
```python
profit = total_sales_revenue - total_returns_amount - total_expenses
```
Содержит:
1. `total_returns_amount` — который включает комиссии.
2. `total_expenses` — который снова включает эти же комиссии (`total_commission`).

**Математическое замыкание (почему 3029 ₽):**
Так как себестоимость ушла в минус (`-2918 ₽`), она попадает в `total_expenses` со знаком минус.
`profit = Выручка - Ложные_Возвраты - (Реальные_Расходы + Минусная_Себестоимость)`
Вычитание отрицательного числа (`- (-2918)`) даёт искусственный плюс к прибыли.
Вот почему дашборд показывает 3029 ₽ вместо 440 ₽.

## ⚠️ ОШИБКА #3: Неинициализированные переменные (NameError)

**Файл:** `routes/analytics.py`  
**Строки:** 395 и 403

В блоке учёта ручных расходов (`Cost`) присутствуют две неинициализированные переменные, которые вызовут `500 Internal Server Error`, если у пользователя есть ручные расходы за выбранный период:

```python
# Строка 395
if len(accruals_data) > 0 and t in ["acquiring", "commission", "logistics", "advertising", "storage"]:
```
Переменная `accruals_data` **не существует** в области видимости функции. Вероятно, должно быть `accrual_items_raw` или `accruals_summary`.

```python
# Строка 403
else: total_manual_expenses += val
```
Переменная `total_manual_expenses` **нигде не объявлена** (`= 0.0`) в начале функции. Это вызовет ошибку `UnboundLocalError`.

## ✅ ВНЕСЁННЫЕ ИСПРАВЛЕНИЯ (01.07.2026)

Все три ошибки устранены в `routes/analytics.py`, функция `sales_report_universal`:

1. **Запрос к БД (строки ~288–300):** В выборку `accrual_items_raw` добавлены поля `OzonAccrual.type_id` и `OzonAccrual.operation_type`, чтобы можно было отличать движение товара от финансовых услуг Ozon.

2. **Переписанный цикл (строки ~310–350):** Себестоимость теперь пересчитывается **только** для строк без `type_id` (`is_product_row = (r_tid is None)`):
   - `val > 0` → продажа: `total_sales_revenue` и `total_cost_price += cp * qty`.
   - `val < 0` → возврат товара: `total_returns_amount` и `total_cost_price -= cp * qty`.
   - Строки с `type_id` (комиссии, логистика, эквайринг) **намеренно пропускаются** в этом цикле, чтобы не искажать себестоимость и не попадать в `total_returns_amount`. Они корректно суммируются во втором цикле (`accruals_summary`).

3. **Блок ручных расходов (`Cost`, строки ~410–420):**
   - Переменная `total_manual_expenses = 0.0` инициализирована в начале функции.
   - Несуществующая переменная `accruals_data` заменена на корректное имя `accruals_summary`.
   - `total_manual_expenses` добавлена в итоговую формулу `total_expenses` и в поле ответа `total_other`.

**Проверка синтаксиса:** `python -m py_compile routes/analytics.py` → `Result: 0` (ошибок нет).

## 🔎 ДОПОЛНИТЕЛЬНАЯ ДИАГНОСТИКА: расхождение скрипта с банком (80 ₽)

После исправления знаков было обнаружено остаточное расхождение между эталонным скриптом и банком Озон за 27.06:

| Показатель | Скрипт (accrual) | Банк Озон | Разница |
|---|---|---|---|
| Доходы | 3173.00 ₽ | 3338.00 ₽ | **+165.00 ₽** |
| Себестоимость | 1076.00 ₽ | 1161.00 ₽ | **+85.00 ₽** |
| Прибыль | 440.45 ₽ | 520.46 ₽ | **+80.01 ₽** |

### Природа расхождения (найдена через `scripts/debug_27_06_discrepancy.py`)

Все услуги (комиссия, эквайринг, логистика, хранение, реклама и т.д.) **совпадают точно**. Расходятся только доходы и себестоимость.

Диагностический скрипт выявил **13 POSTING-записей с `sale_amount = 0`** (помечены `SALE=0!`).
Сырой JSON этих записей показывает:

```json
{
  "unit_number": "78735516-0590-1",      // SKU 2834203781, себестоимость 85 ₽
  "accrued_category": "POSTING",
  "posting": {
    "products": [{
      "sku": 2834203781,
      "delivery": { "services": [{ "type_id": 32, ... }] },  // есть логистика
      "commission": null                                      // НЕТ блока продажи!
    }]
  }
}
```

### Вывод

Это **отмены/возвраты товаров**, по которым Ozon в этот день начисляет только логистические услуги (type_id 29, 32, 45), но **не возвращает `sale_amount`** (он равен 0 или отсутствует). В банке Озон эти позиции всё равно учитываются в доходах и себестоимости, а API `accrual/by-day` их «не видит» как продажу.

**Это не баг знаков и не баг нашего кода.** Это фундаментальное ограничение эндпоинта `/v1/finance/accrual/by-day` — он отражает финансовые начисления, а не движение товара. Поэтому даже эталонный скрипт «теряет» ≈80 ₽ маржи на таких операциях.

### Рекомендация

Для 100% схождения с банком требуется гибридный подход: дополнять данные `accrual/by-day` информацией о продажах из таблицы `OrderProduct`/`OrderPosting` (по постингам, для которых есть `delivery`, но отсутствует `commission.sale_amount`). Реализовано в `scripts/debug_27_06_discrepancy.py` для дальнейшего анализа.
